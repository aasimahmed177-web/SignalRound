# How Fireround works

The lanes feed one schema, every record lands in one table, and every record is read back against its sources before it publishes. This page is the long form of the [README](../README.md)'s "How it works" section; the rules that keep the data honest are in [data-quality.md](data-quality.md), and what each coverage rung turns on is in [coverage.md](coverage.md).

## The lanes

When `COMPANY_REQUESTS=1`, a visitor can submit a public company website from a company search that found no match. The request first checks the homepage using the normal company identity rules, then saves the company profile, runs the checked Deep dive, and verifies each earlier funding round against its own announcement through the history lane. A claim without a verifiable announcement remains in the dossier, not a funding round. Requested rounds are history, never news: they do not enter Latest, Trending, public daily digests, or any notification channel. The request page shows the result and links to the company even if no earlier round was verified. Submissions have a three-per-address daily limit and a global daily cap, and Vercel BotID checks the submit path.

Agents and scripts request companies over MCP. `request_company` takes the company's website and returns the request's `id`, `status`, `step`, `message`, `request_url`, and `company_url` (the company page, which shows the research progress until it is done), or only `company_url` when the company is already covered; `company_request_status` takes the `id` and returns the same fields, so an agent polls it until the status is `done`, `refused`, or `failed`. Both tools call the same code as the page (`submitCompanyRequest` and `companyRequestStatus` in `lib/company-requests.ts`), so the website check, the dedupe (a running request for the domain is returned, never doubled), the three-per-address limit (on a public demo; an admin or a private instance is not counted), and the global cap (`COMPANY_REQUESTS_DAILY_MAX`) count across both doors, and a refusal comes back as a tool error. They skip the origin and BotID checks, which only a browser can pass; the MCP endpoint's own rate limit (on a keyless public demo) and `MCP_API_KEY` still apply in front of them. Over HTTP, `POST /api/company-requests` with `{ "url": "acme.com" }` answers 202 with `{ id, requestUrl, companyUrl }`, 200 with the running request or, for a covered company, `{ companyUrl }`, 400 for a refused website, 403 across origins or for a bot, 429 over a budget (with `Retry-After`), and 404 with the flag off; `GET /api/company-requests/{id}` returns `{ id, domain, status, step, message, tally, brand, dossier, createdAt, companyUrl }`, where `tally` counts the earlier rounds found and verified while research runs `brand` is the homepage's name and logo (null once refused or failed), and `dossier` reports the Deep dive, which can still be running after the request is done: the request finishes once its funding search is verified. The OpenAPI spec lists both only when the flag is on. Whichever door starts it, a requested company's rounds are history and are never delivered.

### Rounds that name no stage

Many large rounds are announced with no stage at all: "$75 million in financing" (Solcoa, September 24, 2026), "a $117m fundraise" (Parallax). The resolver used to drop them as another stage wherever they were read. Now every lane (sweep, monitor, watch, a pasted URL, X, and history) keeps a stageless round by its amount and files it under the preset whose band holds it: under $10M with seed and pre-seed, $10M up to $80M with Series A and B, $80M and more with Series C and later (the cuts that misfile the fewest of the store's lettered rounds since January 2025; `packages/core/src/records/routing.ts`). The row is stored as `other` (or `undisclosed`, or growth at $500M and more) with the label the page writes, and when the page splits the financing into equity and debt the equity figure is the round and the debt sentence rides along as evidence. A lane that reads pages any preset may care about (watch, X, a pasted URL) resolves with every stage a preset keeps and files each lettered round by its stage the same way, the lane's own preset first. A stageless round with no amount stays dropped: every one measured was an award, a grant, a collaboration, or a rumor. A "pre-Series A" (or B, or C) round is stage `bridge`, which the Series A and B preset keeps: before it did, no preset listed `bridge`, and ONYA's and Rio Health's pre-Series A rounds (September 2026) were read seven times between them and dropped every time. Listing `bridge` claims no amount band, so an unlabelled $4M round still files under seed and pre-seed.

### The sweep's seen-state

An hourly day-window sweep's searches return the same articles all day, and each re-read cost five credits and found nothing new. A page a preset's sweep read on a window is not read again for three days on the day window and seven on the week window (`sweep:<preset>:<window>` in `candidates`); a failed read is read again, X timelines are read every time, and a month window (a backfill) reads everything.

## Corroboration and the agent steps

Two more steps run after persist on the rungs that turn them on ([coverage.md](coverage.md)). Corroboration takes a record that just landed and gives it a second reading: when the company's domain is known and no page from it is on the record yet, one `map` of the site (one credit, searched for the company and its round) finds the company's own post or release, which is read first; then one `search` for the company and its round (the name, the lead, the stage, the amount, a word or two on what the company does), up to three more pages (the wire first, then by publisher tier), one extraction each. The company's own page is the source that fixes the day, the amount, and the syndicate when the press has only a republisher's or a roundup's reading. `?lane=corroborate&force=1` on the cron route brings rows with no page from their company's site through this by hand. A page is taken from only when the round it describes is this round: the same company (by name key, domain, or the company named in the title) and facts that agree (the stage, or a different label inside the same week; a stated USD amount within 25 percent; a date within 45 days); a page about another company with the same name is counted as rejected on the run and leaves no trace. A row whose day may be a late page's (borrowed, or a list's week or month) searches the past year instead of the past month, and a page stating the same stage and amount on an earlier day is taken as the round's own announcement, so the read-back that follows can date the row from it (Fearn's June release under a September newsletter's reading). What passes is folded into the record the way Research does, never overwriting a known value, adding a missing date, amount, or lead, more investors, more evidence, and the sources themselves, then rescoring (a row the cross-source read already verified takes the sources and the evidence but no investors: the read-back that follows lists a name only if a source places it in this round); a row in review leaves the queue on its own when the second source lifts it. `pnpm prune-corroboration` re-checks the sources a store attached before this rule and drops the ones about someone else. Standard corroborates new records, Deep new and updated, Max every record. The agent steps follow: Deep and Max gap-fill every new record still in review automatically (the same play as the Research button), and the deep dive runs on its own above $10M on Deep and for every company on Max (where each sweep tick also dives two visible companies still without a checked dossier); Lite and Standard leave both to the buttons. Each step's credits land on the run row's counts (`corroboration_credits`, `agent_credits`); the deep dives run last, after delivery, and each has its own row on Runs.

### Dossiers are checked before they are saved

The agent's dossier reads well and is wrong often enough to matter: funders and accelerators listed as customers, the round we just verified listed again as a "prior round", a total raised from before that round, an employee called a founder, a directory's "similar companies" called competitors. So no dossier is saved, or shown, until it has been checked (`packages/core/src/llm/dossier-verify.ts`, fed by `lib/dossier-check.ts`). Firecrawl reads up to eight of the dossier's own sources (the company's about page and homepage first, then the wires and the press, directories last, LinkedIn and Crunchbase never), two of our rounds' sources, and, when that is thin or has nothing from the company's own site, a five-result search on the name and domain. Our verified record (the rounds with their amounts, stages, dates, and investors, the profile, and the Alexandria facts) is evidence too, and it wins.

A model then rules on every claim: first whether the dossier is about the company in our record at all, then each field and each list item, supported, contradicted, or unsupported, with the exact words that state it. The model is `DOSSIER_VERIFY_MODEL`, or the reconcile model (`RECONCILE_MODEL`, so a Zero Data Retention pin carries over), or GPT 6 Astra, at high reasoning effort. A claim stays only when the model calls it supported and its quote is found in the page it cites (the page as a reader sees it: a link counts as its text, since OpenAI's founders were names linked to profile pages and a quote of the sentence never matched the raw markdown, and a quote shortened with an ellipsis counts when its pieces appear in order); a claim kept on weak footing (low confidence, or a quote not found) gets a second reading and goes unless that one quotes it. What goes:

- A dossier about another company, or one the check cannot place: nothing is saved, and the run on Runs reads `dossier rejected: different company` (or `identity unclear`).
- Customers that are really investors, accelerators, grant programs, or public funders move to Backers; partners, suppliers, and people quoted in a testimonial go.
- Founders the evidence does not call a founder; a founder's role or background that no page states.
- Prior rounds that are one of our rounds under another label, loans, grants, and debt; an amount, date, or lead no page states.
- A total raised below one of our rounds, from before our latest round, or unclear on that point.
- Competitors no page names as a competitor of this company; a headcount or total a newer page contradicts; a one-liner, business model, or "why it matters" with any statement no page makes.

The saved row (schema version 2) is the cleaned dossier plus the check's record: when, which model, the pages read, the search if any, what was kept, every dropped claim with its reason, the page behind each kept claim, and the check's credits. The company page shows a checked dossier as "Checked against N sources"; visitors never see the model's name (Settings shows it). A dossier written before the check (version 1) stays readable to an admin, marked unchecked, and hidden from visitors until the backfill checks it, which rewrites it cleaned or deletes it when it is about another company. A checked dossier stays current until a round that is not history is recorded after it; that round outdates it, and the next sweep or ingest dives the company again (`dossierStates` in `lib/intel.ts`). Until the fresh one lands, the company page leaves out a dossier total the record contradicts and tells an admin which round the dossier predates. When the check cannot run (no model key, the gateway down, nothing readable) nothing is saved: the durable step retries with the agent's result already in hand, and a deep dive does not start at all without a model key.

### History rounds: a company's earlier rounds, each verified on its own

The feed catches the round a company just announced; its earlier Series A and seed are not news and no lane finds them. A checked dossier lists them as prior rounds (the stage and amount as written, a date, the leads), and each is promoted to a real round only when its own announcement is found and read like any record (`lib/history.ts`, the pure rules in `packages/core/src/records/history.ts`, durable in `workflows/history.ts`). For one prior round: one `map` of the company's site for its post about the round, one `search` for its announcement (the name quoted, the label, the amount, the year, the first lead quoted: `"Footprint" Series A $13 million 2024 "QED Investors" funding`), and the pages the dossier check cited for it. The pages are ranked (the company's own post about a raise and the wires first, then the press by publisher tier; a title or slug that names the stage or the amount ranks higher, one that names only another stage lower, directories and social profiles never) and read one at a time, at most five, until one states the round. Each page goes through the same extraction, resolver (grounding, page kind, background and rumor drops, the dating rules), read-back (the reconcile step against its sources, or the judge without a model key), review rules, and persist with its dedupe as any other record. The only differences: the resolver's window is the dossier's date with about a year either side instead of the past week, and a page's round must be the dossier's: the same company, a day (a page that dates nothing cannot place the round, so the next page is read), no contradiction (an amount more than a quarter off, a day outside the dossier's span, another stage), and at least one agreement (the stage, the amount within a tenth, or a day within two weeks), a named lead counting as more evidence. When the amount and the stage agree, a dossier month or year may sit further from the announcement (a July close announced in November); a dossier day keeps the ordinary slack. An undated prior round is never dated from the company's own post unless the round's sentence states the day (a migrated blog republishes a 2024 post as 2026). Nothing skips the read-back: a read that did not run is a failure to retry, never a row. A round with no page that states it stays dossier text, and a round too vague to recognise (a label naming two rounds, no amount, no day) is never searched.

What lands is marked history (`funding_rounds.history`) at its real announced date. A history row is never delivered (never queued, and an outbox row for one is dead-lettered unsent), never new or updated, never followed or ranked by Trending, and not counted in the overview's windowed numbers or the demo's week. The Latest view, the API's list, and MCP's list leave history rows out unless the reader asks for dates (`since` or `until`, as in `/feed?since=2022-01-01&until=2022-12-31`) or, in the API, a company; the RSS, Atom, and JSON feeds never carry one. Company pages list them among the company's rounds, latest first, counted in the total raised, investor pages in the portfolio, and each wears a quiet HISTORY mark. A reading that lands on a round already on the store merges into it by the usual rules and leaves a feed row a feed row: no status change, no delivery; a feed row folded into a history row makes the survivor a feed row with the feed row's read state.

An investor's money figure is its lead share: each round it led counts its stated amount split evenly between the round's leads (`lib/investor.ts`, and the Overview's most active leads in `lib/stats.ts`). One of ten co-leads on a $65B round is credited $6.5B, not $65B, so no firm reads as having led a round others shared, and the figures across firms add up to the money actually led. How co-leads divide a round is rarely disclosed, so the split is even and the page says so ("2 co-led, split evenly"). An investor with no lead seat shows the combined size of the rounds it joined, labelled as round sizes, never as its cheque.

A round shows its own label: "Series D+" is the filter's bucket for every series past C, so a round in it shows the letter its page wrote ("Series H", `stageOf` in `lib/format.ts`) on the company page, the share cards, the feeds, Slack, and the directories, and only filters and facet counts say "Series D+". A company's money figure reads "Raised on record", across the rounds the record holds, because a round the record has not caught is not in it. A dossier's prior round whose series letter a round on the page already carries is the dossier's guess at a label and shows as a plain funding round (Anthropic's dossier called Amazon's $2.75B tranche of March 2024 a "Series E").

Each prior round has one row on a ledger (`history_promotions`: pending, running, promoted, no source, failed, skipped) with what the search found, the pages tried and why each was refused, and its credits, so a promotion is idempotent: a round promoted or with no source found is never searched again, and a dossier saved again with the same rounds queues nothing. A dossier that passes its check (a dive, a re-check, the Deep dive button) queues its prior rounds and starts the company's own pass; a failure is retried after 1 hour, 6 hours, and a day, four tries in all. A prior round dated inside the last week is left for the feed and looked for once the week has passed.

Apollo's funding events arrive the same way, as leads (`lib/apollo.ts`). One the store lacks (a specific equity stage: "Other", an unspecified venture round, debt, and grants are never leads; not a round the store, the ledger, or the dossier already has by stage and time or by figure; Apollo's own repeats folded to one) is written to the ledger with origin `apollo`, its month as the date (Apollo dates every event to the first of a month, and that month can be weeks off), no leads (its investor lists name no lead), and its news link, which is ranked with the pages a dossier cites. It needs no dossier, and from there it is a prior round like any other: the same search, pages, match, and read-back, and no row unless a page states it. The enrichment pass that queued leads starts the company's history pass; the Apollo backfill only queues them, and the history backfill works them. Two more kinds of lead take the same road. A prior round the dossier check dropped only because the pages it read were silent (unsupported, or not confirmed on a second reading; not one it found wrong, ours, or debt) is kept whole on the check's record and queued with origin `check`: the check read eight pages, and the round's own announcement was rarely one of them (Microsoft's investments in OpenAI, most of Crusoe's lettered rounds). And a round an audit found missing is queued by `pnpm fix-records` (`history_lead`, origin `audit`) with the page that states it, which is read first; it is still extracted, resolved, and read back like any lead, and no page means no row. And an earlier round a stealth launch discloses beside the round it announces (Parallax came out of stealth with a $42M seed and a $75M Series A, "$117 million to date", September 2026) is dropped from the feed as background but rides on the later record, and persist queues it with origin `page` and that page: the launch is the only announcement such a round gets, so read for that lead the page keeps the earlier round, dated by the page, instead of dropping it again. A page that merely recalls an earlier round (no stealth launch said, or a day of its own before the page's) leaves it background, since that round had an announcement of its own. Until the round lands, a round whose page stated its funding to date shows that total beside its amount, and the company's raised figure says how far the total runs past the rounds on record. `GET /api/cron/history-rounds` counts the leads by status apart from the dossiers' (`apollo_leads`), so their yield is measured on its own.

### The daily accuracy check

The companies a reader is most likely to look up get a second look every day. At 05:00 UTC a durable run (`workflows/accuracy.ts`) reads the top 100 companies by largest round and by total raised, plus every company with a $100M round, and flags what a reader would notice is wrong: no verified homepage, description, or logo; a round whose stage falls below a verified earlier round, or known only from a weekly list; a round left under the publish bar for a day; a verified total far under Apollo's, or a $100M round Apollo lists that nothing on the store knows; a missing or founderless dossier, or one that dropped a founder; Other on a $100M round; a likely duplicate; no lead on a $50M round. The checks are database reads. The flags go to Review under Accuracy for an admin, clear on their own once fixed, and can be dismissed with a note. Three have a remedy the run starts itself, capped per run: a profile refresh, a deep dive, and a history lead, each still verified by its own lane. The rules and caps are in [data-quality.md](data-quality.md#the-daily-accuracy-check).

## Rules, scoring, and disposition

Every extracted round passes through pure, tested rules in `packages/core`: stage classification, background and rumor drops, dating (page, result, URL), a window check, money parsing with a dated USD rate, investor hygiene, dedupe by company and stage, alias merging, and a confidence score (sources, dated, agreement, publisher tier, evidence) that sets the disposition: publish at 0.75, flag to 0.50, review below. The score is machinery, not a fact about the round, so the tables show what a reader can act on instead: a Verified mark and the source count; the score itself sits in the expanded detail, the API, and the review queue. The rules themselves are listed in [data-quality.md](data-quality.md).

## Durable execution and delivery

Durable execution is the [Workflow SDK](https://workflow-sdk.dev): `workflows/sweep.ts`, `workflows/ingest-candidate.ts`, `workflows/watch-sites.ts`, `workflows/form-d.ts`, `workflows/corroborate.ts`, `workflows/enrich.ts`, `workflows/dossiers.ts`, `workflows/history.ts`, `workflows/trending.ts`, `workflows/announcements.ts`, `workflows/apollo.ts`, and `workflows/accuracy.ts` are steps that retry on their own, and Postgres constraints make re-runs safe. New or updated records fan out through an outbox to Slack (Block Kit via incoming webhook) and Standard Webhooks endpoints (`webhook-id`, `webhook-timestamp`, `webhook-signature`), with backoff and dead-lettering. An email target's rows wait in the same outbox and go out together as one digest per cadence window (daily or weekly, kept under the `digest:<target>` setting), through Resend's HTTP API. Email is optional, for self-hosters who set `RESEND_API_KEY` and `DIGEST_FROM`. Each digest carries an unsubscribe link and `List-Unsubscribe` plus `List-Unsubscribe-Post` headers (RFC 8058 one-click); the link is an HMAC of the target id under the Resend key, and a POST to it (`/api/digest/unsubscribe`) disables that target. A GET only shows a confirm button, so a mail scanner that follows links unsubscribes no one.

Every run prints and stores its rate-card estimate beside the credits measured on the account. Rate card: https://www.firecrawl.dev/pricing

## Backfill

A fresh store starts with one week. To load history, with the dev server running:

```bash
pnpm backfill -- --months 3        # prints the rate-card estimate and stops
pnpm backfill -- --months 3 --yes  # starts it
```

For each preset and each of the last N calendar months (the month to date, then one month back, and so on) it starts one month sweep, and one free SEC Form D run over the same span (EDGAR filings, 100 a page, a week of filings a step). A month sweep costs about what a week sweep costs: search returns the same number of results per query whatever the window, so the bill is the queries plus the pages they turn up, about 630 to 690 credits per preset per month on Lite once verification and enrichment are counted; three months of the three presets is about 5,700 to 6,200 credits. The estimate the command prints prices the searches and page reads alone (about 260 to 320 a preset-month). Watch the runs on `/runs`, where a past month reads "Sweep · Jul 2026". Firecrawl search cannot filter to a past calendar month (its custom date range is accepted and ignored), so an older month searches the past year with the month's name in the query and keeps only results announced inside that month; expect fewer records for an older month than a fresh week finds. The same thing over HTTP is `GET /api/cron/sweep?backfill=3` with the cron bearer; `pnpm backfill` takes `BASE_URL` and `CRON_SECRET` from the environment, so it also points at a deployed instance.

### Dossiers for every visible company

`POST /api/cron/backfill-dossiers` (the cron bearer, not on the schedule) gives every company a visitor can reach (a publish or flagged round) a checked dossier: dossiers written before the check are checked first (no agent run, about 7 to 17 credits each), then the companies with none, or with one a round recorded since has outdated, are dived, newest round first, twenty at a time. `limit` caps each group (a pilot of 5 checks five and dives five), `concurrency` sets how many companies run at once (20, at most 100), `maxTotalCredits` stops new dives once the pass has spent that much (250,000), and `reverifyOnly=1` only checks. A company whose dive failed rests a week, one the check rejected a month, and one being dived by another pass is skipped. The pass is one parent row on Runs (lane Dossiers) with its counts (checked, dived, verified, rejected, removed, failed, credits), and each dive and check has its own row; `GET` on the same route reports the store's dossier coverage and the latest passes. The commands: [deploy.md](deploy.md#dossiers-for-every-company).

### Apollo for every visible company

`POST /api/cron/backfill-apollo` (the cron bearer, not on the schedule) looks up every visible company with a verified domain and no apollo row, ten domains a call, each call a step, until `maxCredits` (15,000) is spent; `limit` caps the companies and `leads=0` writes the rows without queueing leads. It only writes: a row per company (a miss and a namesake too, so the next pass does not pay again), a logo where a company has none and Apollo's loads, and the leads. Runs shows it as one Enrich row (apollo-backfill) with its counts and credits; `GET` reports what Apollo filled (LinkedIn pages and headcounts FullEnrich lacked), the admin signals (headquarters that disagree, totals more than twice ours), and the leads by status. Run the history backfill afterwards to search the leads. The commands: [deploy.md](deploy.md#apollo-for-every-visible-company).

### History rounds for every checked dossier

`POST /api/cron/history-rounds` (the cron bearer, not on the schedule) works every checked dossier with a prior round still to do, then every visible company with an Apollo lead due, newest round first, twenty companies at a time, in fresh runs of twice that many companies like the dossier backfill. `limit` caps the dossiers (a pilot of 10), `concurrency` sets how many companies run at once (20, at most 100), and `maxTotalCredits` stops new companies once the pass has spent that much (25,000). The pass is one parent row on Runs (lane History, backfill) with its counts (prior rounds, searched, sourced, ingested, published, flagged, review, merged, no source, failed, deferred, skipped, credits), and each company has its own row with its credits; `GET` on the same route reports where the prior rounds stand, the latest passes, and the newest history rows. A failed round is left on its backoff for the next pass. A promoted round costs about 11 to 21 credits and one with no source about 30. The commands: [deploy.md](deploy.md#history-rounds-for-every-checked-dossier).

## The database

No database to set up: without `DATABASE_URL` the app uses an embedded Postgres ([PGlite](https://pglite.dev)) under `./data` (`PGLITE_DIR` moves it). It is single-process: a pid lock makes a second command refuse to open it while the dev server runs, so use the dashboard's buttons while the server is up and the CLI when it is not. The database closes cleanly on Ctrl+C; if it ever fails to open, the store is a cache of the web, so `rm -rf data` and run a sweep again. Set `DATABASE_URL` to a Postgres for a deployed instance or to run several processes at once; the schema and migrations are identical. A Neon host is reached over Neon's serverless HTTP driver (nothing to pool on a function), at most 16 queries in flight per process; any other Postgres over `pg`, a pool of 10 per process. `DATABASE_DRIVER=neon|pg` overrides the choice. The app's `DATABASE_URL` should be Neon's pooled URL (the `-pooler` host) on a serverless host; the scripts (`openStore` in `lib/db.ts`) and `pnpm db:migrate` always connect to the same endpoint's direct host, because the pooler runs in transaction mode and drops the session state (a `SET`, `PGOPTIONS`) a script may rely on. The test suite runs against a real server too: `TEST_DATABASE_URL=postgres://... pnpm exec vitest run --no-file-parallelism`.

## Screens

Every dashboard page is a prerendered shell (Next.js Cache Components) that streams its data in, so the first byte is instant on every route. On a public demo a visitor's data comes from the platform's shared cache (`lib/cached.ts`): the feed page for each filter, each company and investor page, News, Runs, and the Slack previews are read from the database at most once a minute while busy and are never served more than three minutes old, so a traffic spike costs the database one read per page a minute instead of one per view; an admin, and every viewer of a private instance, reads them fresh. A company or investor page streams inside the shell, so its own not-found could only answer 200; on a public demo the proxy answers a real 404 first, from a per-process snapshot of every visible id refreshed once a minute (`lib/entity-exists.ts`), so a crawler walking thousands of ids or a burst of made-up ones costs the database nothing extra. On a private instance a missing id still renders the not-found view with the shell's 200. The API routes return real status codes; the dashboard is for people.
